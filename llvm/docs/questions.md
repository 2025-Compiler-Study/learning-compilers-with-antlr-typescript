# 질문 정리

대상 코드: `echo.ll` 과제4

```llvm
define i32 @read() {
  %buf = alloca i32
  call i32 (ptr, ...) @scanf(ptr @.rfmt, ptr %buf)   ; @.rfmt = "%d"
  %val = load i32, ptr %buf
  ret i32 %val
}

define i32 @main() {
  %x = alloca i32
  %y = alloca i32
  %val = call i32 @read()
  %val2 = call i32 @read()
  store i32 %val, ptr %x
  store i32 %val2, ptr %y
  %out1 = load i32, ptr %x
  %out2 = load i32, ptr %y
  call void @write(i32 %out1)
  call void @write(i32 %out2)

  ret i32 0
}
```

## Q1. scanf의 기본 구분자가 공백인가?

정확히는 `scanf`에 "기본 구분자"라는 개념이 없다. **변환 지정자마다** 공백을 다루는 규칙이 있다.

| 지정자                     | 앞쪽 공백을 건너뛰나?             |
| -------------------------- | --------------------------------- |
| `%d`, `%f`, `%s` 등 대부분 | 예                                |
| `%c`                       | 아니요. 공백도 문자 하나로 읽는다 |
| `%[...]`                   | 아니요                            |

- `%d`가 앞쪽 공백을 건너뛰고 **숫자가 아닌 문자에서 멈추기** 때문에 결과적으로 공백이 구분자처럼 동작한다.
- 포맷 문자열 안의 공백은 "공백 문자를 0개 이상 건너뛰라"는 뜻이다. 예: `" %c"`

## Q2. read를 한 번만 호출하고 `42 7`을 입력하면 7은 버려지나?

`scanf`가 7을 지우지는 않는다. **읽지 않은 채 남겨 둔다.**

1. `42 7⏎` 한 줄 전체가 프로세스의 stdin 버퍼에 들어온다.
2. `scanf("%d")`는 `42`를 읽고 그 뒤의 공백에서 멈춘다.
3. 버퍼에는 ` 7⏎`가 남는다.
4. `@read`를 다시 호출하지 않으면 `main`이 끝나면서 남은 버퍼도 함께 사라진다.

남은 입력을 처리하려면 `%*[^\n]`처럼 줄 끝까지 읽어서 버리는 코드를 따로 넣어야 한다.

## Q3. read를 2번 호출하면 scanf도 2번 호출되는데, 어떻게 val과 val2에 나눠 들어가나?

두 번의 `scanf` 호출이 **같은 stdin 버퍼와 읽기 위치**(`FILE` 구조체)를 함께 쓰기 때문이다.
`scanf`는 입력을 미리 나눠 두지 않는다. 매번 **이전 호출이 멈춘 위치부터** 이어서 읽는다.

입력 `42 7⏎`:

```
버퍼:  [ '4' '2' ' ' '7' '\n' ]
위치:    0   1   2   3   4
```

### 첫 번째 `call i32 @read()`

1. `scanf("%d", %buf)`가 호출된다.
2. 버퍼가 비어 있으므로 `read` 시스템 콜을 하고 입력을 기다린다(블록).
3. 엔터를 치면 `"42 7\n"`이 버퍼에 들어온다. 위치는 0이다.
4. `%d`가 처리하는 과정:
   - 앞쪽 공백을 건너뛴다. 위치 0이 `'4'`라서 건너뛸 게 없다.
   - `'4'`, `'2'`를 읽는다. 위치는 2가 된다.
   - 위치 2의 `' '`는 숫자가 아니라서 멈춘다. 이 공백은 **소비하지 않는다.**
5. 42를 반환한다. `%val = 42`

### 두 번째 `call i32 @read()`

1. `scanf("%d", %buf)`가 다시 호출된다.
2. 버퍼에 `" 7\n"`이 남아 있으므로 **시스템 콜 없이** 바로 진행한다. 입력을 기다리지 않는다.
3. `%d`가 처리하는 과정:
   - 위치 2의 `' '`를 건너뛴다. 위치는 3이 된다.
   - `'7'`을 읽는다. 위치는 4가 된다.
   - 위치 4의 `'\n'`에서 멈춘다.
4. 7을 반환한다. `%val2 = 7`

### 정리

- 두 번째 호출이 첫 번째 호출에 이어서 읽는 이유: 버퍼와 위치가 전역 상태(`stdin`)로 남아 있기 때문이다.
- `42⏎`과 `7⏎`을 따로 입력하면, 두 번째 호출이 남은 `'\n'`을 건너뛴 뒤 버퍼가 비어서 다시 시스템 콜을 하고 입력을 기다린다. 결과는 똑같다.

## Arithmetic

대상 코드: `arithmetic.ll`

```llvm
define i32 @remainder(i32 %num1, i32 %num2) {
  %cal1 = sdiv i32 %num1, %num2
  %cal2 = mul i32 %cal1, %num2
  %cal3 = sub i32 %num1, %cal2

  ret i32 %cal3
}
```

### Q. 왜 `a - (a / b) * b`를 한 줄로 쓰지 못하나?

LLVM IR은 **한 명령어가 연산 하나만** 하는 3-주소 코드(three-address code) 형식이기 때문이다. 피연산자 자리에는 레지스터나 상수만 올 수 있고, 다른 연산을 넣을 수 없다.

```llvm
%r = sub i32 %a, %b        ; OK: 레지스터
%r = sub i32 %a, 10        ; OK: 상수
%r = sub i32 %a, (mul ...) ; 불가: 식을 넣을 수 없음
```

이렇게 설계한 이유:

1. **컴파일러가 다루기 쉽다.** 모든 중간값에 이름이 있으니 값이 어디서 만들어지고 어디서 쓰이는지 바로 추적할 수 있고, 최적화도 이 정보를 바탕으로 한다.
2. **계산 순서가 명확하다.** 위에서 아래로 쓴 순서가 곧 실행 순서다.
3. **기계어와 가깝다.** CPU 명령어도 대부분 "레지스터 두 개로 연산 하나" 형태다.

C에서 한 줄로 쓴 식은 clang이 이렇게 펼쳐 준다. ANTLR 계산기의 코드 생성 단계도 같은 일을 한다. AST를 후위 순회하며 자식 노드부터 명령어를 만들고, 그 결과 레지스터를 부모 노드가 피연산자로 쓴다.

```
      (-)                 %t1 = sdiv i32 %a, %b
     /   \                %t2 = mul  i32 %t1, %b
    a    (*)       →      %t3 = sub  i32 %a, %t2
        /   \
      (/)    b
     /   \
    a     b
```

### Q. 소스 코드의 괄호를 기준으로 괄호 안이 위에 오도록 중간 코드가 만들어지고, 그 순서대로 계산되는 건가?

결과적으로는 맞다. **괄호 안의 계산이 중간 코드에서 위쪽에 놓이고, 위에서부터 차례로 계산된다.**

다만 괄호가 직접 "위로 올려라"라고 지시하는 것은 아니다. 중간에 트리가 있다.

1. **파서:** 괄호로 묶인 부분을 AST에서 더 깊은 쪽(자식)에 둔다. 괄호 자체는 이 단계에서 사라진다.
2. **코드 생성:** AST를 후위 순회하며 자식부터 명령어를 만든다. 그래서 깊이 있는 부분, 즉 괄호 안이 먼저 나온다.

LLVM IR에는 괄호뿐 아니라 우선순위라는 개념 자체가 없다. 식을 중첩할 수 없으니 해석할 것이 없고, 줄을 쓴 순서가 곧 계산 순서다. 우선순위와 괄호는 IR보다 앞 단계인 파서에서 모두 처리된다. ANTLR 계산기 문법에서 곱셈을 덧셈보다 먼저 묶도록 규칙을 쓴 것이 바로 이 단계다.

#### 비교: 괄호 하나 차이

**`(a + b) * c`**

```
     (*)              %t1 = add i32 %a, %b    ; 괄호 안이 위로
    /   \             %t2 = mul i32 %t1, %c
  (+)    c
 /   \
a     b
```

**`a + b * c`**

```
   (+)                %t1 = mul i32 %b, %c    ; 곱셈이 위로
  /   \               %t2 = add i32 %a, %t1
 a    (*)
     /   \
    b     c
```

두 번째 예에는 괄호가 없는데도 곱셈이 먼저 나온다. 연산자 우선순위도 괄호와 똑같이 트리 모양을 정하기 때문이다. 괄호는 기본 우선순위를 무시하고 트리 모양을 직접 정하는 수단이다.

#### 순서를 정하는 규칙은 하나다

**값은 쓰기 전에 먼저 만들어져야 한다.** 이 규칙만 지키면 서로 관련 없는 연산은 순서를 바꿔도 결과가 같다.

```llvm
; a*b + c*d
%t1 = mul i32 %a, %b
%t2 = mul i32 %c, %d   ; t1과 t2는 순서를 바꿔도 된다
%t3 = add i32 %t1, %t2 ; t1, t2를 쓰므로 반드시 둘 다 만든 뒤
```

#### 정리

- 괄호와 우선순위가 AST 모양을 정한다.
- AST에서 깊은 쪽이 중간 코드에서 먼저(위에) 나온다.
- 중간 코드는 값 사이의 의존 관계를 지키는 순서로 펼쳐 쓴 것이다.
