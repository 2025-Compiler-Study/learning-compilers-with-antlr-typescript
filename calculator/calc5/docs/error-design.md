# 에러 설계 고민

## Q1. 에러 발견 시 계속 진행해야 하는가, 즉시 멈춰야 하는가?

### 선택지

#### A. Fail-fast — 첫 에러에서 중단

```
에러 발견 → 즉시 반환 → 나머지 AST 빌드 안 함
```

- 구현이 단순하다. 에러 이후 상태를 걱정하지 않아도 된다.
- 개발자가 에러를 하나씩 고쳐야 한다. "fix one, see next" 루프가 반복된다.

#### B. Collect-all — 에러 수집 후 계속 진행

```
에러 발견 → errors[]에 저장 → AST 빌드 계속 → 마지막에 전체 에러 반환
```

- 모든 에러를 한 번에 보여줄 수 있다. TypeScript, Rust, GCC의 방식.
- **연쇄 에러(cascading errors)** 문제가 있다.

```
a = 1;     ← undeclared-variable (에러 1)
b = a + 1; ← undeclared 'b' (에러 2), undeclared 'a' (에러 3)
```

**a 미선언(할당), b 미선언(할당), a 미선언(표현식) — 근본 원인은 2개지만 에러는 3개**

### 연쇄 에러를 줄이는 방향

**에러 sentinel**: 에러가 발생한 변수를 심볼 테이블에 sentinel로 등록해두고, 이후 같은 변수 참조에서는 에러를 발생시키지 않는다.

```
a = 1;     → 'a' 미선언 에러 → symbolTable에 a를 sentinel로 등록
b = a + 1; → 'a' 참조 시 sentinel이면 에러 스킵 → 'b' 미선언만 보고
```

**에러 복구(Error Recovery)**: 에러를 만나면 다음 동기화 지점(`;` 또는 `}`)부터 재개한다. ANTLR 파서 수준에서 기본 내장된 기법이다.

### 현재 구현

Collect-all이지만 연쇄 에러를 처리하지 않는다. 에러 sentinel은 향후 개선 포인트다.

## Q2. 컴파일러 에러를 내장 Error 객체로 확장하는 것이 의미 있는가?

### 현재 구조

```
Error (JS 내장)
└── CompilerError  (abstract, span 포함)
    └── SemanticError  (kind + name 추가)
```

### Error를 상속할 때 실제로 얻는 것

| 속성               | 유용성                                                         |
| ------------------ | -------------------------------------------------------------- |
| `message`          | ✅ 그대로 사용                                                 |
| `stack`            | ❌ AstBuilder 내부 스택이 찍힘. 소스 위치는 `span`이 이미 담당 |
| `name`             | △ `this.constructor.name` 자동 설정. 로그에는 편리             |
| `instanceof Error` | △ throw할 경우에만 의미 있음                                   |

### Error 상속이 보내는 잘못된 시그널

`extends Error`는 관례적으로 "throw 가능"을 의미한다.
`SemanticError`는 throw되지 않고 배열에 저장된다.
코드를 읽는 사람이 "이거 어디서 throw되지?"라고 찾게 만드는 인지 비용이 생긴다.

### 대안: 순수 데이터 클래스

```typescript
export class SemanticError {
  constructor(
    public readonly kind: SemanticErrorKind,
    public readonly name: string,
    public readonly span: SourceSpan,
    public readonly message: string,
  ) {}
}
```

Rust/Haskell에서 에러는 그냥 enum/record 타입이다. `Result<T, E>`로 에러를 값으로 다루는 방식이 "에러는 데이터다"라는 사고를 더 명확히 표현한다.

### Error 상속이 합리적인 경우

- throw도 하고 배열에도 저장하는 이중 용도가 필요할 때
- 외부 라이브러리가 `instanceof Error` 체크를 요구할 때

### 결론 (미결)

"throw하지 않는 에러에 Error를 상속하는 것"은 관례보다 관성에 가깝다.
순수 데이터 클래스가 의도를 더 명확하게 표현하지만, JS 생태계 관습상 `extends Error`도 실용적인 선택이다.

현재 구현을 유지하거나 순수 데이터로 바꾸는 것, 둘 다 합리적이다.

## Q3. AST 빌드 시 체크되는 에러와 실행 중 발생하는 에러는 어떻게 다른가?

### 핵심 질문: "이 에러를 감지하려면 무엇이 필요한가?"

에러를 감지하는 데 **코드의 구조**만 필요한지, 아니면 **실행 중의 값**이 필요한지가 구분 기준이다.

- 코드 구조만으로 알 수 있다 → **정적(static)** 감지 가능
- 실제로 실행해봐야 안다 → **동적(dynamic)**, 런타임에서만 감지 가능

```
int a;
int a;    ← "a가 이미 선언됐다"는 것은 코드를 읽는 것만으로 알 수 있다 → 정적

int a;
b = 10 / a;  ← a가 0인지는 실행해봐야 안다 → 동적
```

---

### 인터프리터 관점

인터프리터는 소스 코드를 기계어로 변환하지 않고, **AST를 직접 순회하며 즉시 실행**한다. 별도의 "컴파일된 바이너리"가 없기 때문에 단계가 단순하다.

```
소스 코드
    ↓
AstBuilder  ←  이 시점이 인터프리터의 "빌드 시점" (정적 분석)
    ↓
Executor    ←  이 시점이 인터프리터의 "런타임" (동적 실행)
```

우리 프로젝트에서 에러가 발생하는 위치:

| 에러                  | 발생 위치    | 이유                                  |
| --------------------- | ------------ | ------------------------------------- |
| 미선언 변수           | `AstBuilder` | 코드 구조만으로 알 수 있음            |
| 재선언 변수           | `AstBuilder` | 코드 구조만으로 알 수 있음            |
| `a = 1 / 0;` (리터럴) | `Executor`   | 구조로 알 수 있지만 현재 구현이 안 함 |
| `b = a / c;` (변수)   | `Executor`   | 실행해봐야 c가 0인지 알 수 있음       |

`1 / 0`은 정적으로 감지할 수 있는데도 현재 Executor에서 잡고 있다. 이는 구현을 단순하게 유지하기 위한 선택이다.

---

### 컴파일러 관점 (C, Rust 같은 언어)

컴파일러는 소스 코드를 **기계어 바이너리로 변환**한다. 실행은 나중에 별도로 이루어진다. 단계가 더 많다.

```
소스 코드
    ↓
파싱 + 의미 분석  ←  "컴파일 시점" (정적)
    ↓
코드 생성 (기계어 바이너리 생성)
    ↓
[나중에 별도 실행]
    ↓
실행             ←  "런타임" (동적)
```

GCC로 다음 C 코드를 컴파일하면:

```c
int x = 1 / 0;
```

```
warning: division by zero [-Wdiv-by-zero]
```

컴파일 시점에 경고를 낸다. 이것이 **상수 폴딩(constant folding)**이다. 피연산자가 리터럴이므로 컴파일러가 "이 식은 항상 0으로 나누게 된다"는 것을 컴파일 중에 계산해낸다.

반면 다음 코드는 컴파일러가 경고를 낼 수 없다:

```c
int a = read_input();
int x = 10 / a;  ← a가 0인지는 실행해봐야 안다 → 컴파일러 침묵
```

이 경우 0으로 나누기는 런타임에 하드웨어 예외(SIGFPE)로 발생한다.

---

### 인터프리터 vs 컴파일러, "런타임"의 의미가 다르다

|                | 인터프리터                         | 컴파일러                                |
| -------------- | ---------------------------------- | --------------------------------------- |
| 정적 분석 시점 | AstBuilder 단계                    | 컴파일 단계                             |
| 런타임         | Executor가 AST를 직접 실행하는 중  | 생성된 바이너리가 OS 위에서 실행되는 중 |
| `1 / 0` 처리   | 현재 Executor에서 잡음 (개선 가능) | 컴파일러가 경고 발생                    |
| `a / b` 처리   | Executor 실행 중 잡음              | 바이너리 실행 중 하드웨어 예외          |

핵심 차이: 컴파일러는 "정적 분석"과 "실행" 사이에 **코드 생성** 단계가 있다. 인터프리터는 이 단계 없이 AST에서 바로 실행한다. 그래서 인터프리터에서 "빌드 시점"이라고 부르는 것이 컴파일러에서는 "컴파일 시점"에 해당한다.

---

### 현재 구현 요약

```
AstBuilder  →  정적 분석: "이 코드가 실행될 수 있는 상태인가?" (구조 검사)
Executor    →  동적 실행: "실행 중에 무슨 값이 나왔나?" (값 검사)
```

`1 / 0` 같은 상수 나누기는 AstBuilder에서 감지할 수 있는 여지가 있다. 현재는 구현 단순화를 위해 모든 나누기 체크를 Executor에 위임하고 있다.

0이 코드 내부에 있는 케이스와 사용자에게 동적으로 받은 값이 0인 경우 같은 에러지만 같다고 볼 수 있는가?
